Ringkasan Arsitektur
State Management

flutter_bloc v9

BLoC per fitur dengan event/state yang terdefinisi baik. Penggunaan sealed class untuk events sudah modern.

Dependency Injection

get_it + service locator

Semua dependency di-register di service_locator.dart. Abstrak via interface (IQuranRepository, dst).

Data Layer

Cache-first + offline

SQLite (sqflite) untuk cache lokal. Network client dengan HTTPS enforcement, timeout, dan max response size.

Audio

just_audio + background

LockCachingAudioSource untuk streaming + cache offline otomatis. Mendukung lock screen controls.

Responsive

Two-pane layout

Breakpoint-aware: compact (phone) → two-pane (tablet/landscape). Menggunakan Material 3 breakpoints.

Localization

EN + ID (ARB)

Flutter gen-l10n dengan file .arb. Locale bisa diset manual atau follow device.

✅ Kekuatan: Arsitektur sudah sangat bersih, layer separation jelas (data/feature/core/shared), interface-driven sehingga mudah di-test dan di-swap implementasinya.

Bug & Risiko Potensial
Bug Critical Sleep Timer "End of Surah" tidak pernah ter-trigger
SleepTimerBloc memiliki opsi SleepTimerOption.endOfSurah, namun komentar di code menyatakan "The caller is responsible for firing SleepTimerCancelled when playback completes." Masalahnya: tidak ada kode di PlayerBloc atau listener manapun yang memanggil event ini ketika PlaybackStatus.completed tercapai. Fitur ini tidak berfungsi.
File terkait: lib/features/sleep_timer/bloc/sleep_timer_bloc.dart • lib/app.dart (SleepTimerBloc listener)
// Di app.dart — hanya menangkap status 'expired', bukan trigger-nya
BlocListener<SleepTimerBloc, SleepTimerState>(
  listenWhen: (prev, curr) => curr.status == SleepTimerStatus.expired,
  listener: (ctx, _) => ctx.read<PlayerBloc>()
    .add(PlayerPauseRequested()),
  // ⚠️ Tidak ada listener di PlayerBloc untuk completed → SleepTimerCancelled
)
Fix: Di app.dart, tambahkan BlocListener kedua yang memantau PlayerBloc: ketika status menjadi PlaybackStatus.completed DAN sleep timer aktif dengan opsi endOfSurah, panggil SleepTimerCancelled() dan PlayerPauseRequested().
Bug High Download progress memukul database SQLite pada setiap chunk data
Di DownloadServiceImpl._startDownload(), method _updateProgress() dan _notifyListeners() dipanggil di dalam loop await for (final chunk in response.stream). Setiap chunk (bisa ratusan per detik) melakukan 1 DB write + 1 DB read penuh (getAll()). Ini dapat menyebabkan UI jank parah dan database lock pada perangkat lemah.
File terkait: lib/data/services/download_service_impl.dart (baris loop stream)
// ⚠️ Kode saat ini — DB write + read tiap chunk!
await for (final chunk in response.stream) {
  sink.add(chunk);
  received += chunk.length;
  final progress = received / total;
  await _updateProgress(...); // DB WRITE setiap chunk
  _notifyListeners(); // getAll() = DB READ setiap chunk
}

// ✅ Fix: throttle update setiap 5% atau setiap 500ms
var lastNotifyTime = DateTime.now();
var lastProgress = 0.0;
await for (final chunk in response.stream) {
  sink.add(chunk); received += chunk.length;
  final progress = received / total;
  final diff = progress - lastProgress;
  final elapsed = DateTime.now().difference(lastNotifyTime);
  if (diff >= 0.05 || elapsed.inMilliseconds >= 500) {
    await _updateProgress(...);
    _notifyListeners();
    lastProgress = progress;
    lastNotifyTime = DateTime.now();
  }
}

Isu Performa
Performance High AyahView scroll tidak di-debounce — AyahLoadMoreRequested bisa terfired berkali-kali
Method _onScroll() di AyahView langsung memanggil bloc.add(AyahLoadMoreRequested()) setiap kali scroll event masuk dan posisi kurang dari 300px dari bawah. Scroll cepat bisa mengirim puluhan event identik dalam hitungan milidetik, menyebabkan banyak network request duplikat.
File: lib/features/ayah/view/ayah_view.dart
Fix: Terapkan pola yang sama dengan _ListPaneState._onScroll() di search_screen.dart — gunakan Timer _scrollDebounce dengan delay 200ms, dan guard dengan flag isLoadingMore di AyahState untuk mencegah double-load.
Performance High PlayerBloc menerima position stream setiap ~200ms — rebuild terlalu sering
PlayerBloc subscribe ke 3 stream sekaligus (positionStream, durationStream, playbackStream). Position stream dari just_audio default fire setiap ~200ms saat playing. Setiap emit memanggil add(_PlayerPositionUpdated) yang membuat event baru di BLoC queue — sekitar 5 event/detik. Ini normal untuk seekbar, tapi semua subscriber PlayerBloc ikut re-evaluate.
File: lib/features/player/bloc/player_bloc.dart
Sudah dimitigasi sebagian dengan BlocSelector + view-model di player_panel.dart. Namun bisa dioptimalkan lebih lanjut dengan men-throttle position stream di service level:

get positionStream => _player.positionStream.distinct().throttleTime(Duration(milliseconds: 250));

Tambahkan paket rxdart atau implementasi throttle manual.
Performance Medium SearchBloc debounce menggunakan pola Completer yang tidak lazim
Di SearchBloc._onQueryChanged(), digunakan Completer manual untuk menunggu debounce Timer — ini membuat setiap event membuat Completer baru yang tidak akan pernah di-cancel jika event berikutnya datang. Meski tidak crash, ada memory allocation yang tidak perlu dan potensi kebocoran jika debounce dicancel tapi completer tidak di-complete.
File: lib/features/search/bloc/search_bloc.dart
Saran: Gunakan transformer debounceTime dari rxdart atau gunakan pola yang lebih sederhana: cukup simpan query terakhir dan cek di dalam callback Timer apakah query masih sama sebelum emit.
Performance Medium "Continue Listening" chip menggunakan linear search O(n) tiap tap
Di _HeaderActions dalam search_screen.dart, ketika chip ditekan, code melakukan searchState.surahs.firstWhere(...) dan searchState.reciters.firstWhere(...). Untuk 114 surah ini trivial, tapi pola ini tetap bisa dioptimalkan dengan Map lookup O(1) yang disiapkan di BLoC state.
Saran: Tambahkan getter di SearchState: Map<int, Surah> get surahMap yang computed sekali dari list. Gunakan surahMap[lp.surahNumber] untuk lookup O(1).
Performance Medium SurahTile tidak menggunakan itemExtent meski komentar menyebutnya
Komentar di SurahTile menyebutkan "All tiles have a fixed layout height of 76 px so the parent ListView can use itemExtent", namun di _ResultsList dalam search_screen.dart, ListView.builder tidak menggunakan itemExtent. Tanpa ini, Flutter tetap harus melakukan layout measurement per tile meski ukurannya sudah dideklarasikan konstan.
File: lib/features/search/view/search_screen.dart
// ✅ Tambahkan ini ke ListView.builder di _ResultsList
ListView.builder(
  controller: scrollController,
  itemExtent: 86, // 76px tile + 10px padding vertical
  addRepaintBoundaries: false, // sudah pakai RepaintBoundary manual
  ...
)

Isu Usability
UX High Impact Reciter picker muncul setiap kali tap surah — mengganggu alur cepat
Setiap kali user mengetuk surah, modal reciter picker selalu muncul — bahkan jika reciter yang diinginkan sama seperti sebelumnya. Ini memperlambat alur "tap to play" menjadi 2 langkah wajib.
Rekomendasi: Jika searchState.selectedReciter != null, langsung play dengan reciter tersebut tanpa menampilkan picker. Tampilkan reciter saat ini sebagai badge kecil di sebelah kanan surah tile. Hanya tampilkan picker jika user long-press atau tekan ikon reciter secara eksplisit.
UX High Impact Bookmark tertanam di Settings — tidak intuitif dan sulit ditemukan
Daftar bookmark dan fungsi "tambah bookmark" tersembunyi di dalam halaman Settings. User tidak dapat langsung membookmark surah yang sedang diputar, dan melihat bookmark memerlukan navigasi ke Settings → Bookmarks.
Rekomendasi: Pindahkan bookmark ke dedicated screen atau bottom sheet yang bisa diakses dari player panel (ikon bookmark di header). Tambahkan tombol bookmark di PlayerPanel._Header (sejajar tombol ayah & close) yang langsung memanggil BookmarkAddRequested.
UX Medium Speed chip: long-press untuk menu tidak discoverable
Fitur long-press pada _SpeedChip untuk memilih kecepatan langsung tidak memiliki affordance visual. User baru tidak akan tahu ada menu tersembunyi di sana.
Rekomendasi: Ganti dengan DropdownButton atau PopupMenuButton yang menampilkan ikon dropdown kecil, atau tambahkan tooltip "Hold to pick speed" saat pertama kali player dibuka.
UX Medium AyahView tidak menampilkan nama Surah dengan benar
Header AyahView hanya menampilkan "Surah [number]" (nomor) tanpa nama surah. Jika ayahs.isNotEmpty, nomor surah bisa didapat tapi nama Inggris/Arab tidak ditampilkan. Juga tidak ada informasi juz atau jumlah total ayah.
Rekomendasi: Simpan data Surah lengkap di AyahState (bukan hanya ayah items), lalu tampilkan "Al-Fatihah • Surah 1 • 7 Ayah" di header. Tambahkan nama Arab di sebelah kanan.
UX Medium Tidak ada indikator status offline yang terlihat oleh user
App sudah mendeteksi koneksi via ConnectivityService dan melempar OfflineException, tapi tidak ada banner atau snackbar yang memberi tahu user secara proaktif saat koneksi terputus/pulih.
Rekomendasi: Tambahkan StreamBuilder atau BlocListener di root app yang memantau ConnectivityService.onConnectivityChanged dan menampilkan SnackBar "Offline — Menggunakan data cache" / "Kembali online" sesuai kondisi.
UX Medium Tidak ada tombol "Next/Previous Surah" di player panel
Setelah satu surah selesai, player berhenti (PlaybackStatus.completed) dan user harus kembali ke list untuk memilih surah berikutnya. Tidak ada navigasi antar surah dari player itu sendiri.
Rekomendasi: Tambahkan event PlayerNextRequested / PlayerPreviousRequested ke PlayerBloc. Player bloc perlu referensi ke SearchBloc state (via constructor injection atau event parameter) untuk mengetahui surah mana yang "next". Auto-play next saat PlaybackStatus.completed bisa dijadikan opsi di Settings.
UX Label bookmark di Settings hanya menampilkan nomor surah
Item bookmark menampilkan "Surah 1" dan edition ID mentah seperti "ar.alafasy" — bukan nama yang user-friendly. User tidak bisa langsung tahu surah mana yang di-bookmark.
Rekomendasi: Enrichment bookmark data saat load: join dengan surah list untuk mendapatkan nama Inggris, dan format edition ID menjadi nama qori yang terbaca (misalnya "ar.alafasy" → "Mishary Alafasy").

Fitur yang Disarankan

🔁 Repeat & Auto-play Mode

Tambahkan mode repeat one (ulangi surah yang sama) dan auto-next (lanjut ke surah berikutnya otomatis). Fondasi sudah ada di PlayerBloc, tinggal tambahkan state RepeatMode.

📚 Navigasi Juz

Tambahkan filter/group by Juz (1–30) di search screen. Data juz sudah tersedia dari API AlQuran Cloud. Membantu user yang membaca mengikuti rutinitas harian.

⬇️ Download dari Player Panel

Tombol download langsung di PlayerPanel header untuk surah yang sedang diputar. DownloadBloc sudah tersedia, tinggal wiring UI.

☁️ Cloud Sync (Phase 3)

Interface ICloudSyncService sudah ada dengan stub NoOpCloudSyncService. Tinggal implementasi dengan Firebase Firestore atau Supabase untuk sync bookmark antar device.

🔔 Notifikasi Download Selesai

Setelah download selesai, tidak ada feedback selain update status di list. Tambahkan local notification (paket flutter_local_notifications) agar user tahu meski app di background.

📋 Riwayat Mendengarkan

Log surah-surah yang pernah diputar beserta durasi. Bisa dibangun di atas tabel SQLite baru. Berguna untuk statistik ibadah harian/mingguan.

🔍 Cari Berdasarkan Isi Ayah

Pencarian saat ini hanya berdasarkan nama surah. Tambahkan full-text search pada tabel ayah di SQLite menggunakan FTS5 untuk mencari kata/frasa dalam teks Arab atau terjemahan.

🎨 Widget Ayah Favorit

Izinkan user menyimpan ayah individual sebagai favorit (bukan hanya seluruh surah). Tampilkan ayah favorit sebagai widget di home screen menggunakan home_widget package.

Fitur Local Storage (Offline-First)
📋 Konteks Database: App sudah memiliki SQLite (sqflite) dengan 7 tabel — surahs, editions, bookmarks, downloads, ayahs, translations, settings — plus dua folder file: audio_cache/ (LockCachingAudioSource) dan audio_downloads/ (manual download). Semua fitur di bawah ini memanfaatkan infrastruktur yang sudah ada tanpa butuh dependency baru.
Feature Local 📥 Pre-download Teks Ayah untuk Mode Offline Penuh
Tabel ayahs dan translations sudah ada di schema DB, namun hanya terisi saat user membuka AyahView (on-demand). Belum ada cara untuk men-download seluruh teks Quran + terjemahan sekaligus agar bisa dibaca offline penuh tanpa pernah membuka setiap surah satu per satu.
Tabel yang digunakan: ayahs • translations

Upgrade OOP & Prinsip SOLID
🎯 Catatan: Arsitektur keseluruhan sudah sangat baik — interface-driven, clean separation of concerns, BLoC pattern konsisten. Temuan di bawah ini adalah refinement untuk mendekati kode yang ideal, bukan perbaikan kritis. Setiap item dilengkapi contoh Before (kode saat ini) dan After (rekomendasi).
S Single Responsibility Principle — setiap class hanya punya satu alasan untuk berubah
S
Tinggi QuranRepositoryImpl._composeTracks — fungsi "komposisi" dengan side effect tersembunyi
Method _composeTracks(surahs, editions) terlihat sebagai fungsi komposisi murni, tapi diam-diam meng-assign _surahsMemoryCache dan _recitersMemoryCache sebagai side effect. Ini melanggar SRP karena satu method melakukan dua hal: membangun track list sekaligus memperbarui dua cache. Sulit di-test dan rawan bug urutan pemanggilan.
❌ Before
List<Track> _composeTracks(
  List<Surah> surahs,
  List<Edition> editions,
) {
  // ... filter reciters ...
  // ⚠️ side effects!
  _surahsMemoryCache = surahs;
  _recitersMemoryCache = reciters;
  return <Track>[...];
}
✅ After — value object
// Value object — immutable, pure
class _ComposedData {
  final List<Surah> surahs;
  final List<Edition> reciters;
  final List<Track> tracks;
  const _ComposedData({...});
}

_ComposedData _compose(
  List<Surah> s, List<Edition> e) {
  // pure — no side effects
  return _ComposedData(...);
}
S
Tinggi PlayerBloc._describeAudioError — logika klasifikasi error ada di dalam BLoC
BLoC seharusnya hanya mengatur alur state. Medium BookmarkBloc — event chaining internal (add(BookmarkLoadRequested())) menciptakan hidden coupling
Handler _onAdd dan _onDelete setelah selesai memanggil add(const BookmarkLoadRequested()) untuk reload. Ini adalah event chain tersembunyi yang tidak terlihat dari luar. Low Surah.fromJson vs Surah.fromMap — dua factory constructor redundan dengan logika serupa
Surah memiliki fromJson(Map<String, dynamic>) untuk API response dan fromMap(Map<String, Object?>) untuk SQLite row. Kedua method hampir identik, hanya berbeda di type signature. Ini violates DRY dan membuat pemeliharaan double — perubahan field harus diupdate di dua tempat.
